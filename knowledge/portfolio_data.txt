PROJECT 2 — AI ON-CALL: VOICE AGENT FOR IT SUPPORT (CHAPTER II):

AI On-Call is an outbound voice AI system deployed as a pilot case in April 2026. The core problem it solves is the elimination of manual follow-up phone calls that IT support dispatchers had to make whenever an ITSM ticket was opened. Before this system existed, a human dispatcher had to call the customer, verify who they were speaking to, collect their description of the issue and estimated time of arrival, and then manually enter that information back into the ITSM ticketing system. This was repetitive, time-consuming, and error-prone. AI On-Call removes the human dispatcher from this loop entirely, automating the full call lifecycle from trigger to ticket update.

The way it works is as follows. When an ITSM ticket is created or reaches a specific status, a webhook fires and triggers the AI On-Call FastAPI backend. LangGraph manages the conversation flow as a stateful agent graph, maintaining the state of the call across turns. The system uses Twilio to initiate an outbound phone call to the customer's number associated with the ticket. Once the customer answers, the LangGraph agent conducts a spoken conversation in natural language through Twilio's voice streaming APIs. The agent first verifies the caller's identity by asking them to confirm a 6-digit security code that was sent to them or is associated with their account — this critical step prevents the agent from sharing sensitive ticket information with the wrong person. After identity is verified, the agent collects a work note describing the issue and the customer's estimated time of arrival or resolution. The agent handles variations in how customers describe things, clarifies when needed, and confirms the information collected back to the customer before ending the call. Once the call is complete, all collected data including the identity verification result, the work note, and the ETA is pushed back into the ITSM system via an n8n webhook, and the ticket is updated automatically. Zero human dispatcher involvement was needed at any step.

The problem solved is real and measurable: it eliminates an entire category of manual follow-up work that was previously handled by a human for every ticket. The system is a direct bridge between classical RPA thinking — automate the repetitive human step — and modern agentic AI — give the agent natural language reasoning to handle variation. Twilio handles both outbound call initiation and the real-time voice stream; LangGraph provides the stateful reasoning; n8n provides the webhook glue between the ITSM system and the agent backend.

The tech stack is Python and FastAPI for the backend API, LangGraph for the stateful conversation agent logic and flow management, Twilio for outbound voice call initiation and voice streaming, n8n for ITSM integration and bidirectional webhook handling, Redis for state persistence during active calls, and Langfuse for LLM tracing and observability of every conversation step. The GitHub repository is at github.com/georgelush/AI-ON-Call and a YouTube demo video is available on George's channel showing the system in action during a live test call. Status is Pilot Case as of April 2026, meaning it has been tested and validated with real call flows.


PROJECT 3 — PRODUCTION RAG SERVICE: HYBRID SEARCH API (CHAPTER III):

The Production RAG Service is a production-grade, multi-tenant RAG API shipped in April 2026, built from first principles to implement the full 2026 enterprise RAG stack. This is not a simple RAG demo — it is a complete backend API designed to handle real-world requirements at scale: multiple tenants with isolated namespaces, high-quality retrieval through hybrid search combining two complementary retrieval strategies, a reranking stage for maximum answer relevance, async document ingestion with error recovery, streaming answer delivery so users do not wait, JWT-based security, Prometheus monitoring, and full Langfuse observability at every pipeline stage.

The architecture begins with document ingestion. The system accepts documents through an async ingest queue, supporting 13 different file formats including PDF, Word, text, markdown, code files, and audio files. Audio files are automatically transcribed using Whisper before indexing, making the system fully multimodal. When a document arrives it is chunked into passages, embedded using OpenAI embedding models, and indexed into Qdrant as both dense vectors for semantic similarity and sparse BM25 vectors for keyword matching. The dead-letter queue (DLQ) captures documents that fail to ingest, preserving them for retry or inspection rather than silently losing them — a critical requirement for production reliability.

For retrieval, the system uses hybrid search combining dense vector similarity and sparse BM25 keyword search. Dense search finds passages that are semantically similar to the query even when exact words do not match. Sparse search finds passages that contain the exact keywords from the query. Both sets of results are fused together using Reciprocal Rank Fusion (RRF), which produces a unified ranked list that consistently outperforms either method alone. This fused list is then passed through a cross-encoder reranking sidecar which scores each candidate passage against the query for precise relevance, producing the final top passages that are sent to the language model for answer generation. This two-stage retrieval and reranking pipeline represents the 2026 state of the art in production RAG.

Answers stream back to the client via Server-Sent Events (SSE) so users see the response building in real time rather than waiting for the full completion. The system implements namespace-scoped RBAC with JWT authentication, meaning each tenant's data is fully isolated from others and access is controlled by signed tokens. Prometheus metrics expose the system's performance and health for external monitoring dashboards. Langfuse provides per-stage tracing so every retrieval, reranking, and generation step is observable, debuggable, and auditable.

The tech stack is FastAPI, Qdrant, Redis, Langfuse, OpenAI, Pydantic v2, and Docker. The GitHub repository is at github.com/georgelush/rag-system. A YouTube demo walkthrough is available on George's channel. Status is shipped as of April 2026.


PROJECT 4 — AGENT ORCHESTRATOR: MULTI-AGENT AI SYSTEM (CHAPTER IV):

The Agent Orchestrator is George's flagship live project, started in May 2026, and it is deployed and fully accessible at georgelush.github.io/Portfolio/agent-chat.html. It is a multi-agent AI system where a LangGraph StateGraph orchestrator receives every visitor message and routes it to the right specialist agent using Groq's llama-3.3-70b-versatile model for intent classification. Every routing decision and every agent step streams live to the chat UI via Server-Sent Events, giving visitors full real-time visibility into which agent is working and what it is doing at each moment. The agent graph is rendered visually in the UI, and the active agent glows with its assigned color while its progress text appears in a live bubble above the final response.

The system has six agents. The RAG Agent uses ChromaDB and sentence-transformers all-MiniLM-L6-v2 for local free embedding to answer any question about George's background, projects, skills, experience, and contact information from a comprehensive knowledge base. The model is pre-baked into the Docker image at build time so startup is fast. The Email Agent uses Gmail API with OAuth2 to send George's CV as an attachment to any email address the visitor provides. It authenticates using a long-lived refresh token stored as an environment variable and delivers the CV PDF directly to the visitor's inbox. The Calendar Agent collects five required fields from the visitor — name, email, preferred date, preferred time (Romania EEST timezone), and meeting topic — then saves the pending request to Upstash Redis with a 24-hour TTL and sends a Telegram notification to George with an inline keyboard Approve or Reject button. When George taps Approve, the agent creates a Google Calendar event with a Google Meet link and emails the visitor a confirmation. When George taps Reject, the visitor receives a polite email explaining the time is unavailable. The Job Match Analyzer agent accepts either a job posting URL or raw job description text pasted directly into the chat, auto-detects which was provided, fetches and parses the URL if needed, and then analyzes the role against George's complete background. It calculates a fit score from 0 to 100 percent, identifies the top three strengths where George maps directly to the role's requirements, identifies one honest gap with context on how George addresses it, and offers to generate a tailored cover letter addressed to the recruiter. After analysis it sends a Telegram notification to George with the role title, company, fit score, and JD snippet so George always knows when a recruiter analyzed his profile. The Telegram Agent handles instant notifications and is wired into both the HITL calendar approval and job match notification flows. The Orchestrator itself is the sixth agent, routing every incoming message and synthesizing results from whichever specialist was called.

The backend is built with FastAPI and deployed as a Docker container on Hugging Face Spaces at port 7860. The Dockerfile uses a CPU-only PyTorch build to keep the image lightweight. Upstash Redis REST API is used for HITL state persistence because in-memory dictionaries reset on container restarts while Upstash persists across all requests and deployments. The frontend is a single vanilla HTML file with no framework, using fetch and ReadableStream to consume the SSE events and animate the agent graph live in the browser. contextvars.ContextVar is used for thread-safe SSE queue passing between the FastAPI handler and the LangGraph graph invocation.

Tech stack: LangGraph, FastAPI, Groq, ChromaDB, sentence-transformers, SSE Streaming, Docker, Hugging Face Spaces, Telegram Bot API, Upstash Redis, Gmail API, Google Calendar API. What is Human-in-the-Loop (HITL) and has George implemented it? Human-in-the-Loop (HITL) is a design pattern where an automated system pauses at a critical decision point and requests human approval before proceeding. George has implemented HITL in production in the Calendar Agent of the Agent Orchestrator. When a visitor requests a meeting, the agent collects all required information, saves it to Upstash Redis with a 24-hour TTL, and sends George a Telegram message with an inline keyboard showing Approve and Reject buttons. The system then waits. When George taps Approve, it automatically creates a Google Calendar event with a Google Meet link and emails the visitor. When George taps Reject, it emails the visitor a polite decline. The state is stored in Upstash Redis rather than in-memory precisely because Hugging Face Spaces containers can restart at any time and in-memory state would be lost. In his most recent professional role, George also architected HITL approval systems for critical operational decisions in manufacturer workflows.
